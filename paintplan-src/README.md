# PaintPlan — source

Plan and practise paintings from a photo (values, notan, palette, limited-palette mixing, contours, composition
guides, positioning on a real canvas size). Plain HTML/CSS/JS — no framework, no npm dependencies for the build.

Live:
- Classic: https://pgosko.github.io/Test-apps/paintplan/
- Liquid Glass (preview): https://pgosko.github.io/Test-apps/paintplan/proposals/liquid-glass/

## Layout

```
build.mjs                 zero-dependency build (Node ≥ 18)
src/
  shell.html              page skeleton (head/meta, <style>s, body, <script>) with {{placeholders}}
  styles/base.css         structure + component styles shared by all themes (uses design tokens)
  partials/               markup shared by theme templates ({{> posbar}}, {{> print-area}})
  core/                   logic + state, no theme knowledge
    util.js  config.js  store.js  pipeline.js  storage.js  image.js  sample.js  placement.js  geometry.js  levels.js
    paint-library.js      ~60 standard artist oils (name, CI pigment codes, reference colour, opacity, tinting strength,
                          source). GENERATED by research/build-library.py — see research/oil-paints.md
  worker/
    client.js             spawns the engine as a Blob worker (works offline and on iOS Safari) + main-thread fallback
    engine/               pure image processing, concatenated into function ENGINE(){…}
      color.js image-cache.js filters.js values.js palette.js mixing.js edges.js dispatch.js
  ui/                     DOM ↔ state controllers
    panel.js mode-info.js histogram.js scale-info.js render.js overlays.js gestures.js picker.js export.js init.js
    paint-picker.js (searchable paint picker for Limited Palette slots; bottom sheet on phones)
    setup.js (Setup toggle)  empty.js (empty state)  pwa.js (SW registration + update toast)  boot.js
  pwa/sw.js               service worker template      pwa/manifest.webmanifest   manifest template
  assets/                 icons (a theme may override with themes/<id>/assets/)
  themes/<id>/
    theme.json            name, title, theme colour, deploy path, manifest names, SW options, runtime config
    theme.css             design tokens (:root{…}) + component/layout overrides on top of base.css
    template.html         body markup: where header, stage, panel and mode bar go
    icons/*.svg           (optional) referenced from theme.css as {{icon:name}}
dist/<id>/                build output — what gets deployed (index.html is a single file with CSS+JS inlined)
research/                 oil-paints.md (sources + method), build-library.py, raw scraped data
test/                     headless Chrome tests (functional, histogram, palette, service-worker update, visual parity)
archive/                  old proposals (Studio, Atelier, Instrument — static, not maintained), v1/v2 artifacts, old tests
```

The modules share one script scope and are concatenated in the order listed in `build.mjs` (`MODULES`). The app
keeps shared mutable state (current photo, processing results, settings `S`) in top-level variables; converting it
to native ES modules would have required rewriting that state handling (and risking behaviour changes), so the
source is split by concern into files, and `build.mjs` does the bundling. Each file starts with a one-line header
saying what it is for. `THEME` (the theme's `runtime` config + build hash) is available to every module.

## Changing a design (theme only)

Edit `src/themes/<id>/theme.css` (tokens and styles) and, if the arrangement changes, `template.html`. Element ids
that the logic uses must stay (e.g. `#view`, `#stage`, `#panel`, `#panelBody`, `#modes`, `#posbar`, `#file`,
`#bPos`, `#bMirror`, `#bFit`, `#bPng`, `#bPanel`). Panel sections are generated by `ui/panel.js` with stable ids
(`secMode`, `dCanvas`, `dComp`, `dGrid`, `dLines`, `dView`, `dExport`, `dTips`) so themes can style or move them.
Theme behaviour switches live in `theme.json → runtime`:
- `sample`: `true` = built-in sample image + Sample button (classic); `false` = empty state (`#empty` in the template).
- `setup`: `null`, or `{title, hint, sections:[…], hide:[…], open:[…]}` — the Setup toggle (`#bSetup` in the template);
  `sections` are shown only in Setup, `hide` only outside it (build.mjs generates the CSS).

## Adding a theme

Copy `src/themes/classic` (or `liquid-glass`) to `src/themes/<new-id>/`, change `theme.json` (title, colours,
`deploy` path, manifest names, `sw.legacyCaches: []`), restyle `theme.css`/`template.html`, run `node build.mjs`.
The new theme gets its own `dist/<new-id>/` with its own service worker and cache prefix (`paintplan-<new-id>-`).
If it is deployed *inside* another theme's folder (like the preview under `paintplan/proposals/`), add that
sub-path to the outer theme's `sw.exclude` so the outer worker never caches it.

## Adding a feature

1. Logic/state in `src/core/` (pure image processing that should run off the main thread goes in
   `src/worker/engine/` and is dispatched from `dispatch.js`; add the file to `ENGINE_PARTS` if new).
2. Controls in `src/ui/panel.js` (markup + `setState`), wiring in `src/ui/init.js`, drawing in `src/ui/render.js`.
3. New files: add them to `MODULES` in `build.mjs` (optionally with `if: rt => …` to include per theme).
4. Style the new controls in `styles/base.css` (and per theme if needed). Run the tests.

## Build, test, deploy

```
node build.mjs                          # → dist/classic, dist/liquid-glass
sh test/run-all.sh                      # build + functional + service-worker + visual-parity tests
node build.mjs --deploy ../test-apps    # copy dist/* to the repo paths in theme.json + source to paintplan-src/
cd ../test-apps && git add -A paintplan paintplan-src && git commit -m "…" && git push origin main
```

Tests need Chrome (`/usr/bin/google-chrome`) and `playwright-core` reachable from `test/node_modules`.
`test/parity.js` compares against the pre-refactor files (`PP_BEFORE`, default `/workspace/_backup_pre_refactor/paintplan`).

## Service worker & updates (no manual version bump)

`build.mjs` stamps every build with a content hash (index.html + sw.js + manifest + icons). The hash is the cache
name (`paintplan-<theme>-<hash>`) in `sw.js` and `THEME.build` in the page (also `<meta name="paintplan-build">`).
Any change → new sw.js bytes → browsers install it on the next visit (`skipWaiting` + `clients.claim`), and the old
cache is deleted. Strategy: pages are **network-first** (revalidated, cached copy only when offline / after 4 s),
icons/manifest are stale-while-revalidate. If a new worker takes over while an older page is open (e.g. an installed
iPhone app resumed from the background), a small "PaintPlan was updated — Reload" toast appears. The classic worker
ignores `proposals/` (previews have their own worker) and deletes the legacy `paintplan-v1` cache.
